# 赛事管理平台 PRD

版本：0.3；更新：2026-10-05；状态：结构与全平台前端已交付，前端反馈进入下一SDD规划，其他领域未决项保留。
依据：本次用户访谈。本文整理已确认需求，不代表所有首版范围、赛制参数和技术方案已确定。

## 1. 产品定位与问题

面向卡牌与格斗游戏的赛事组织者、参赛者，提供从创建、报名、编排、报分到确认推进和结果展示的管理平台。
用户希望处理多阶段、重新排种子、指定晋级位置及特殊判罚，减少手工维护对阵和参赛数据。
上述问题来自产品访谈，尚无运营数据量化其发生频率或成本。

参考 start.gg、Challonge 的阶段、种子和对阵能力；本平台按自己的业务模型设计。
重点是可定义的赛事结构与正确对阵，自动安排比赛时间后置。

## 2. 目标、成功标准与范围

### 2.1 产品目标

1. 用户能创建赛事并报名，按赛事关系获得相应操作权限。
2. 主办方能组合比赛阶段、分组、选手池和晋级分配，或套用模板后调整。
3. 已支持赛制按冻结的规则生成正确对阵，错误配置可定位和解释。
4. 收齐整轮赛果后，由主办方确认推进，已确认赛果不可修改。
5. 模拟赛事可展示完整进行中与已完成状态，核心边界可重复验证。

### 2.2 近期与后续

| 类别 | 内容 | 确认状态 |
|---|---|---|
| 产品核心 | 账号、赛事、报名、权限、赛制编排、报分、整轮推进、结果展示 | 用户已提出；各模块首版细节未冻结 |
| 自定义创建 | 多阶段、阶段内分组、选手池、重排种子、晋级分配、模板、合法性检查 | 方向已确认；具体参数和编辑边界待定 |
| 首版赛制 | 单败、双败淘汰、循环、固定轮数瑞士、Major 风格瑞士 | 调研候选，非全部首版承诺 |
| 个人/组队 | 用户初始范围含个人和组队报名 | 是否同时进入首版待定 |
| 后置 | 自动时间排程、已推进后的回滚改判、取消资格（回溯）、退出者移出配对 | 用户明确暂不实现 |
| 暂未纳入 | 收费支付、外部游戏自动取分、直播运营、积分评级系统等 | 未提出，不自动扩展范围 |

P0/P1 的模块和赛制排序属于规划建议，须在首个相关 change 中明确；不得把所有产品需求自动列为首版 P0。

### 2.3 验收指标

以下为建议采用的工程验收门槛，尚未形成真实运营指标：

- 每个纳入范围的需求都有规格场景、实施任务和可观察验收方式。
- 已支持赛制的独立算例与预期一致；预期不能由被测算法生成。
- 非法比分、权限不足、结果未齐、轮次已锁定等场景均有明确处理。
- 重复或并发确认不会重复推进，也不会产生部分锁定、部分晋级状态。
- 进行中、已完成和异常样例可以按固定输入重复构建。
- 有限测试不宣称穷尽所有配置或证明竞赛公平性。

运营指标候选：赛事创建完成率、办赛完赛率、配置错误率、人工更正次数。
真实目标、采样范围、人数规模、并发量和性能预算待验证，本文不编造百分比或期限。

## 3. 用户与权限

| 用户关系 | 用户目标 | 已确认能力/待细化 |
|---|---|---|
| 未登录访问者 | 查看赛事和结果 | 公开访问范围待确认 |
| 注册用户 | 管理资料、创建赛事、加入赛事 | 已确认；注册登录方式待定 |
| 赛事创建者/主办方 | 设置规则、管理报名与赛果、推进 | 已确认；详细权限待定 |
| 参赛选手 | 报名、查看对阵、提交赛果 | 已确认；提交冲突处理待定 |
| 受邀管理员/协作者 | 承担部分办赛工作 | 主办方分配权限已提出；角色、授权范围待定 |
| 队长/队员 | 组队报名和管理名单 | 产品候选；首版范围待定 |

账号不是互斥的“主办方账号/选手账号”。同一用户可在不同赛事担任不同关系。
“主办方”和“管理员”在访谈中均指赛事内管理人员；谁能裁决、二次确认、推进由权限规格定义，不能假定所有管理员权限相同。

个人中心提供注册/登录、我的资料、我创建的赛事、我参加的赛事。
“我管理的赛事”还可能包含受邀协作赛事，入口组织方式待设计确认。

## 4. 业务术语与对象

| 概念 | 含义 |
|---|---|
| 赛事系列 | 聚合多届独立赛事，例如高校杯系列 |
| 独立赛事 | 有自己的报名、规则、阶段和结果，例如第一届高校杯 |
| 比赛阶段 | 一段完整的瑞士轮、循环赛或淘汰赛，可包含多个轮次 |
| 阶段内小组 | 同一阶段内的分组；不等同于跨阶段选手池 |
| 选手池 | 接收来源选手、整理与重新排种子、再向阶段分配的模块 |
| 轮次 | 同一推进单位中的对阵集合，例如八强四场或瑞士某轮全部对阵 |
| 对阵/整场 | 两个参赛单位之间的一场比赛，可包含多局 |
| 单局 | 有局序号、双方选择和该局结果的明细 |
| 种子 | 编排顺序；是否等同于对阵图固定位置需明确 |
| 目标落位 | 目标阶段、小组或比赛位置；不同于泛指种子排名 |
| 晋级分配规则 | 来源筛选、排序、目标、位置映射及名额规则 |
| 双方判负 | Double Loss，同一对阵两方都记负 |
| 双败淘汰 | Double Elimination，胜败者组赛制，与双方判负不同 |
| 退出状态 | 弃权或取消资格引发的持续自动判负状态 |

“瑞士轮 + 瑞士轮 + 淘汰赛”中的各项是阶段，不是单个对局轮次。
BO1/BO3/BO5 属于整场的局数规则；联赛/杯赛是赛事组织形式。
“出轮”暂指某阶段结束或退出该阶段；后续进入哪个阶段由分配规则确定，不能默认所有出轮者晋级。

## 5. 用户故事与主流程

- US01：作为用户，我能创建或参加赛事，以便从个人中心进入对应工作。
- US02：作为主办方，我能定义赛事信息、阶段及规则，以便按实际办赛结构运行。
- US03：作为主办方，我能套用并调整模板，以便减少重复配置。
- US04：作为主办方，我能按组名次、战绩或种子分配选手，以便完成阶段衔接。
- US05：作为选手，我能提交赛果，以便主办方汇总本轮结果。
- US06：作为管理人员，我能修改尚未确认的结果、执行特殊判罚并二次确认。
- US07：作为主办方，我能确认整轮并推进，以便冻结成绩并产生下一轮。
- US08：作为查看者，我能看到赛事进行状态、对阵和最终结果。

建议主流程（需要后续规格冻结状态与操作时机）：
创建赛事/套用模板 → 配置并校验 → 发布与报名 → 整理名单/种子 → 开始阶段 →
生成本轮对阵 → 上传/裁定赛果 → 收齐并确认整轮 → 锁定结果/生成下一轮 →
阶段结束 → 按规则分配至下一阶段 → 完赛展示。

最终轮的确认应结束阶段或赛事，不能机械地生成无意义的下一轮；行为待对应规格明确。
不同小组是否分别确认轮次，以及双败淘汰交错轮次的推进单位尚待决定。

## 6. 功能需求与验收

以下 R 编号供 OpenSpec 引用。状态“确认”表示用户需求已提出；不代表实现、上线优先级或细节全部确定。

### R01 账号与个人中心【确认】

注册/登录、我的资料、我创建/管理的赛事、我参加的赛事。
验收：同一账号可同时具有办赛和参赛记录；不同赛事关系不相互授予权限。
待定：登录渠道、资料字段、受邀协作入口、密码恢复。

### R02 赛事系列与基础信息【确认】

独立赛事可归入系列；创建时选择赛事信息和规则，支持分类/分组。
验收：不同届赛事的报名和结果相互独立；阶段属于具体赛事。
待定：分类标签、系列权限、发布/取消/删除规则、信息字段和可见性。

### R03 报名与选手信息【确认方向，首版范围待定】

个人/组队报名、收集选手数据。
验收：报名绑定具体赛事，已收集字段可供授权管理人员使用。
待定：字段配置、审批、重复报名、候补、签到、名单锁定；队长/成员/替补规则。
不得在规格中自行增加敏感信息收集字段。

### R04 权限分配【确认】

主办方可向管理人员分配不同操作权限。
验收：报分、修改、判罚、规则编辑、轮次推进分别有权限检查。
角色矩阵、授权粒度、移交和撤权行为待定；界面隐藏操作不能替代服务端权限检查。

### R05 模块化赛事编排【确认】

创建多个阶段、阶段内分组、选手池、重排种子、指定晋级阶段/顺位。
验收候选：
- 瑞士阶段A → 选手池重排 → 瑞士阶段B → 瑞士阶段C → 淘汰阶段。
- 阶段A分四组进行淘汰；某些组冠军分配至阶段B，另一些进入阶段C。
- 来源阶段3-0选手可映射至后续阶段指定顺位。
待定：创建时预设或结束后人工分配、池合并排序、同分、名额、人工覆盖、编辑锁定。

### R06 赛制与对局配置【确认方向】

用户选择已有赛制及参数，平台不假装支持未实现算法。
对每个实际支持的变体定义适用人数、种子、轮空、轮数/阈值、配对、积分、同分和排名。
是否允许平局由创建赛事的规则控制。平局积分和淘汰赛决胜方式待定。

### R07 模板与配置合法性【确认】

预设可套用并修改，非法配置提供具体定位与原因。
校验建议（未批准完整设计）：
- 静态：参数范围、引用、循环依赖、筛选重叠、目标位置冲突、名额容量。
- 开赛前：真实名单、重复进入、保留名额、种子/落位和轮空。
- 推进时：赛果、处罚、输出名额、阶段输入就绪。
未有实际人数或未来赛果时不能声称静态验证已保证运行成功。
配置可执行不等于竞赛公平；规则版本和模板快照建议由设计明确。

### R08 赛果提交与明细【确认整场需求，逐局方案待定】

选手和主办方均可提交。整场支持胜负平、数字比分、DQ/弃权等特殊原因。
建议拆开整场结果、数字比分、结束原因和发生方，而不是用“DQ”替代数字字段。
用户提议记录逐局顺序、角色/卡组等；是否必填、卡组完整程度、截图/证据和公开范围未确认。
验收：非法比分或不允许的结果不能成为可确认赛果。
待定：任一方提交是否算收齐、双方冲突、重复提交和管理员裁定的记录方式。

### R09 整轮确认、推进与锁定【确认】

淘汰赛和瑞士轮都须收齐本轮所有对阵赛果，由主办方统一确认进入下一轮。
确认后整轮赛果不可修改，回滚改判后置。
验收：
- 缺任一必须提供的赛果时不能完成确认。
- 单场赛果收到不自动推进该场下游对阵。
- 确认后本轮全部锁定，产生对应下一轮。
- 重复/并发确认只推进一次；失败不能产生部分状态（工程验收建议）。
待定：轮空与系统自动结果怎样满足“收齐”、循环赛确认方式、组级轮次、最终轮和阶段间操作顺序。

### R10 特殊判罚【确认】

管理员选择特定选手执行以下操作，均要求二次确认，当前轮次确认推进前可修改：

| 操作 | 已确认影响 | 尚待定义 |
|---|---|---|
| 本轮判负 | 当前轮次失败 | 对手结果、比分和积分 |
| 本轮弃权 | 当前轮次弃权失败 | 与本轮判负的统计差异 |
| 弃权 | 后续配对自动记对应失败，不可改 | 当前场未提交时怎样结算、排名 |
| 取消资格 | 后续配对自动记对应失败，不可改 | 奖项、排名和展示 |
| 取消资格（回溯） | 后置 | 已确认赛果和下游回溯范围 |

持续退出者仍参与配对；移出配对后置。
退出者若出轮并进入下一阶段，状态延续并继续自动判负，不能仅因退出状态阻止进入。
具体出轮/分配路径未定；不能误读成所有淘汰者都强制进入下一阶段。
处罚在当轮确认前可修改与后续自动结果不可修改的时间边界，需要规格明确撤销影响范围。

### R11 双方判负与赛制兼容【确认】

循环/瑞士支持双方判负，管理员和系统可使用；只配置是否允许选手提交。
允许双败的阶段中，两名退出者相遇记双方判负。
淘汰赛暂禁用双方判负，包括选手、管理员及系统生成。
该限制不禁止双败淘汰赛制。
验收：选手提交开关关闭仍可由系统记双败；淘汰赛的双败输入被拒绝。

未解决冲突：两个持续自动判负的选手在淘汰赛相遇。
不得擅自选胜者、移除选手、轮空晋级或给出冠军；该场景的行为需在涉及它的实施前确定。

### R12 公开展示与模拟数据【确认方向】

提供进行中和已完成赛事样例：基本信息、阶段/分组、对阵、比分、排名和最终结果。
每个已支持赛制有正常、边界、异常和完整办赛样例。
具体页面布局、通知渠道、实时更新方式、导出和平台后台范围待设计，不自动列为首版必做。

## 7. 赛制调研交付要求

[初始证据](FORMAT-RESEARCH.md) 是研究线索，不是算法完成声明。

| 候选赛制 | 需冻结的主要规则 |
|---|---|
| 单败淘汰 | 种子位置、轮空、胜者流向、排名与季军赛 |
| 双败淘汰 | 胜败者组映射、重赛规避、交错轮次、决赛重置 |
| 单/双循环 | 配对覆盖、主客/先后手、积分、同分、退出 |
| 固定轮数瑞士 | 同分/跨分组配对、重赛、轮空、平局、积分、破同分 |
| Major 风格瑞士 | 胜负阈值、初始/动态种子、Buchholz变体、BO切换、出轮分配 |
| 多阶段组合 | 来源筛选、池合并、重排、固定落位、跳阶段、名额和成绩继承 |

每个变体形成：官方来源及版本 → 规则与配置范围 → 算法方案 → 无解处理 → 独立算例。
不能混用不同游戏、赛事或年份规则。Buchholz有变体，Major-like模板必须冻结具体版本。
两方都负、平局、退出和轮空对配对/积分的影响分别定义。

## 8. 业务约束与非功能要求

已确认：正确对阵优先、结果整轮锁定、处罚二次确认、权限分配。
设计建议（待规格确认）：关键操作记录操作者/时间/原因，保留原始提交与裁定轨迹；
并发提交和确认采用明确版本/幂等策略，自动结果保留生成原因。
动态对阵应能重放同一输入，随机种子如有使用需记录。
实际人数上限、性能、可用性、部署、安全细节和资料访问范围未定。
不继承旧教学文档的“无认证/无测试”简化条件作为本平台需求。
